# @platform/cosmos

This package gives the process its one Cosmos DB for NoSQL database, and an in-memory stand-in for tests. Access is keyless: the identity holds Cosmos DB Built-in Data Contributor on the database and nothing wider, so local authentication stays off on the account and nothing here holds a secret.

- `container` — the interface every store is written against: `read`, `create`, `patch` (`set` operations, conditional on an etag with `ifMatch` or on a predicate with `condition: "FROM c WHERE …"`), `delete`, `query` and `batch`, each in one named partition. A query never fans out across partitions, and the type says so. A refusal is a `CosmosStatusError` carrying the service's status (409 a taken id, 412 a condition that no longer holds, 404 a batch operation on nothing); a missing document is a null, never an error. `ContainerDefinition` is how a package declares the containers its store reads: a name, the partition key path, the composite indexes an `ORDER BY` over several fields needs.
- `client` — the one `CosmosClient` on `azureCredential()`: `COSMOS_ENDPOINT` names the account, `COSMOS_DATABASE` the database (default `app`). The SDK retries throttling after the wait the service names, a bounded number of times; a request has a deadline of its own. `COSMOS_KEY` is for the emulator only.
- `sdk` — the layer over `@azure/cosmos`. The SDK reports a refusal in three ways (a thrown error, a read's status, a batch's per-operation results); each becomes one `CosmosStatusError`. A failed batch is refused with the status of the operation that failed, rather than the 424s of those rolled back with it. A query drains every page the service answers in; a store that pages a person's list pages by a keyset of its own, never by the service's continuation token.
- `access` — `checkCosmos(containers)`, the startup check. It reads the database and each declared container, so the start fails if a container is missing or partitioned otherwise than its store addresses it (a point read in the wrong partition answers nothing, not an error). It also fails for a container declared with `itemTtl` that keeps no lifetime for its documents: that container would silently ignore a document's own lifetime, and what was written to remove itself would stay. A 403 is `awaiting-roles`: the template assigns the data-plane role in the deployment that starts the replica, and an assignment can take minutes to apply.
- `deployment-rules` — a production process refuses to start with `COSMOS_KEY` set.
- `emulator` — `provisionEmulator` makes the database and containers on the emulator, as the template makes them for a deployment. It serves `bun run migrate` on your machine, the tests and CI. It uses the key only; a deployment's identity may not create a container. A container that was made before its definition asked for lifetimes is given them.

The containers themselves are declared in the template (`infra/modules/cosmos.bicep`) with their indexing policies. `infra/cosmos.test.ts` checks that every container the backend's stores declare matches the template's partition key and composite indexes.

`@platform/cosmos/testing` holds the in-memory stand-in and a shared suite that checks it behaves like the service:

- `fakeCosmosDatabase(definitions)` — the interface in memory. It refuses what the service refuses, with the service's status: an id its partition holds, an etag or a condition that no longer holds, a patch of the id or the partition key or of more than ten operations, a batch of more than a hundred operations or of more than 2 MiB. It scopes every read, query and batch to one partition. It applies a batch to a copy that replaces the original only when every operation succeeded, and it answers copies.
  - Its SQL is the subset the stores write (`SELECT [TOP n] * FROM c [WHERE …] [ORDER BY …] [OFFSET n LIMIT m]`, `IS_DEFINED`, `IS_NULL`, three-valued as the service's predicates are). Anything outside it throws rather than answering differently.
  - It keeps no index, so it answers an `ORDER BY` the service would refuse for want of a composite index; only the emulator run catches that.
- `cosmosContract(emulator)` — the shared suite, written against the interface alone, for the conflict, the precondition, the partition scoping, the query order and the batch (the 400 refusals are checked on the stand-in only). It runs in memory always, and on the emulator under `COSMOS_TESTS=1` with `COSMOS_ENDPOINT` and `COSMOS_KEY`, which is how CI runs it. A case the emulator fails is a gap to record against the real service, never a case to loosen.
- `fakeCosmosDatabase(definitions, now?)` — the stand-in itself, on a clock the caller may name. A container declared with `itemTtl` drops a document `ttl` seconds after its last write, as the service does where the container's time to live is on with no default. A `ttl` that is not a positive whole number or -1 is refused on any write. Like the 400 refusals, this is checked on the stand-in only.
- `openTestCosmos(definitions)` — a database for one suite, installed as the process's: in memory, or on the emulator under a throwaway name, dropped after. Every store suite runs on it, so the same assertions meet the stand-in here and the emulator in CI.
